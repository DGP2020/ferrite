# ADR-0004: Dual-Layer Translation with Deterministic FFI Generation

**Date**: 2026-10-19
**Status**: accepted
**Deciders**: Ferrite Architecture Team

## Context

When LLMs are prompted to write C-compatible Rust functions directly, they invariably output C-ABI signatures (`extern "C"`) cluttered with raw pointers (`*mut c_char`, `*const i32`), manual pointer arithmetic, null checks, and pervasive `unsafe` blocks. Such code is essentially "C written with Rust syntax"—it fails to provide memory safety, cannot leverage Rust's standard collection abstractions, and creates an enormous unsafe attack surface.

Conversely, expecting LLMs to write both safe idiomatic Rust AND complex unsafe FFI marshaling in a single turn frequently results in subtle lifetime mismatches, undefined behavior at the ABI boundary, and compilation failures.

## Decision

Partition translation into a strict **Dual-Layer Translation** architecture:
1. **Idiomatic Safe Rust Core**: The language model writes only pure, memory-safe Rust with zero `unsafe` blocks, utilizing idiomatic types such as `&[T]`, `&mut [T]`, `&str`, `Option<T>`, and `Result<T, E>`.
2. **Deterministic Companion FFI Wrapper**: Ferrite automatically and deterministically generates an `extern "C"` companion wrapper (`ferrite_<name>`) using battle-tested code templates. The wrapper validates pointer non-nullness, constructs safe slices with length checks, calls the safe Rust function, and marshals returns back across the C ABI.

The same companion FFI wrapper is utilized both in the differential fuzz harness (Stage 4) and in the hybrid integration library (Stage 6).

## Alternatives Considered

### Alternative 1: Single-Layer Direct FFI Generation by LLM
- **Pros**: Only one code entity generated; no companion wrapper layer needed.
- **Cons**: Resulting Rust code is littered with `unsafe` blocks, raw pointers, and C-like idioms.
- **Why not**: Violates Ferrite's core objective of producing safe, idiomatic Rust; unsafe code generated by LLMs frequently harbors latent memory bugs.

### Alternative 2: Transpilation via C2Rust Followed by LLM Unsafe Lifting
- **Pros**: Preserves raw syntactic equivalence initially.
- **Cons**: Transpiled C2Rust code consists of hundreds of unsafe pointer dereferences, unions, and goto statements that LLMs struggle to refactor without introducing behavioral regressions.
- **Why not**: Green-field translation against clean safe signatures guided by differential verification yields significantly safer and cleaner code.

## Consequences

### Positive
- 100% memory-safe Rust core implementation with zero unapproved `unsafe` blocks.
- Unsafe FFI boundary code is isolated to deterministically generated, audited templates.
- Uniform FFI interface shared seamlessly between the differential test harness and hybrid project builds.

### Negative
- Requires maintaining FFI code generation templates for all supported parameter types and combinations.
- Slight indirection overhead for function calls crossing the FFI companion wrapper.

### Risks
- Complex C data structures (nested heap graphs, self-referential structs) require sophisticated FFI template marshaling; deferred to Phase 2 with strict boundary validation.
