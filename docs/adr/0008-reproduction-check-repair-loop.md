# ADR-0008: Two-Phase Reproduction Check for Counterexample Repair

**Date**: 2026-10-21
**Status**: accepted
**Deciders**: Ferrite Architecture Team

## Context

When differential fuzzing identifies an input that causes the Rust translation to diverge from the C implementation, blindly passing the raw fuzz finding directly into an LLM repair prompt often fails. In many instances, the discrepancy may be non-deterministic, flaky, or caused by harness initialization issues rather than a genuine translation bug.

Furthermore, invoking a full 10,000-iteration differential fuzzing campaign to evaluate every single candidate fix generated by an LLM repair prompt is prohibitively slow and wastes significant token budget and CPU time on candidate fixes that do not even resolve the original trigger input.

## Decision

Implement a **Two-Phase Reproduction Check** protocol for the counterexample repair loop:

1. **Phase 1 (Pre-Prompt Confirmation)**: Before dispatching a repair prompt to the LLM, Ferrite synthesizes a minimal standalone Rust unit test asserting the expected behavior on the counterexample input. It compiles and runs this test against the failing translation. Only if the test **fails as expected** is the failure confirmed and the repair prompt constructed with the failing test and exact assertion diff.
2. **Phase 2 (Post-Repair Validation)**: Upon receiving a candidate patch from the LLM, Ferrite immediately re-executes the standalone reproduction test against the patched code. Only if the reproduction test **passes cleanly** does Ferrite re-launch the full differential fuzzing campaign. If it fails, an escalated repair prompt is dispatched with the concrete compiler or assertion failure.

## Alternatives Considered

### Alternative 1: Direct Re-Fuzzing without Pre-Check or Unit Test Synthesis
- **Pros**: Fewer moving parts; avoids code synthesis of standalone Rust unit test files.
- **Cons**: High latency per repair attempt (running full fuzzer every turn); no defense against non-reproducible or flaky counterexamples.
- **Why not**: Causes prompt thrashing and wastes model token budget on invalid or non-reproducible inputs.

### Alternative 2: Interactive Human-in-the-Loop Triage for All Divergences
- **Pros**: Human developer verifies each failure and crafts custom repair instructions.
- **Cons**: Destroys end-to-end automation; halts agent migration runs until a developer intervenes.
- **Why not**: Incompatible with autonomous agentic migration and offline benchmarking workflows.

## Consequences

### Positive
- Zero wasted repair tokens on flaky, non-reproducible, or harness-induced errors.
- Immediate, lightweight sub-second validation of candidate repairs before triggering heavy fuzz campaigns.
- Automatically generates permanent, standalone Rust regression tests for every repaired defect in `ferrite-out/<fn_name>/repro_test.rs`.

### Negative
- Requires templating and synthesizing valid Rust unit tests for all supported input types and values.
- Adds a small compile step for the reproduction test before each repair prompt.

### Risks
- Complex stateful counterexamples might require multi-step call sequences to reproduce; handled in L3 verification via serialized operation traces (`RingBufOp`).
